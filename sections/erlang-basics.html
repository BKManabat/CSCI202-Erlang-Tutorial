Match a value before choosing a clause

{add, 3} is a tuple. The atom add names an operation and the integer 3 supplies its amount. In {add, Amount} = {add, 3}, pattern matching binds the unbound variable Amount to 3. Variables begin with an uppercase letter or underscore. Unquoted atoms begin with a lowercase letter [1].

Variables cannot be reassigned. After that match, Amount = 4 fails because the bound value is still 3. Functions use multiple clauses and guards to choose behavior. The first clause whose pattern and guard succeed is evaluated [1].

Run a counter process

Install Erlang/OTP and run erl from a terminal. Save the following module as counter_demo.erl in the directory where you start the shell. The module name and filename must match.

-module(counter_demo).
-export([start/0, add/2, stop/1]).

start() ->
    spawn(fun() -> loop(0) end).

add(Pid, Amount) ->
    Ref = make_ref(),
    Pid ! {add, self(), Ref, Amount},
    receive
        {Ref, Value} -> Value
    after 1000 ->
        timeout
    end.

stop(Pid) ->
    Pid ! stop.

loop(N) ->
    receive
        {add, From, Ref, Amount} when is_integer(Amount) ->
            Next = N + Amount,
            From ! {Ref, Next},
            loop(Next);
        stop ->
            ok
    end.

spawn starts the counter and returns its process identifier, or PID. Pid ! Message sends a message. Sending does not wait for the receiver to handle it. A receive expression takes a matching message from the mailbox [2].

1> c(counter_demo).
{ok,counter_demo}
2> Pid = counter_demo:start(), counter_demo:add(Pid, 3).
3
3> counter_demo:add(Pid, 4).
7
4> counter_demo:stop(Pid).
stop

The two additions return 3 and 7. The value stop is returned by the send expression. It does not acknowledge that the process has already terminated.

Carry state through recursion


The first update computes Next = 0 + 3, replies with 3, and calls loop(3). The next update runs with N = 3. No existing variable is reassigned. The recursive call is the last operation, so the loop does not accumulate pending returns [3].


self() supplies the caller's PID. make_ref() creates a reference that lets the caller recognize this request's reply. It does not detect duplicate updates.


Account for messages that do not match


The counter leaves hello in its mailbox because neither receive clause matches it. A later valid request can still be handled. Repeated unmatched messages retain memory and can make mailbox searches longer [2, 3]. An addition with a noninteger amount also fails the guard and remains queued.


The one-second timeout bounds the caller's wait. It does not cancel the request. An update may happen after the timeout, and retrying can apply the addition twice. A late reply can remain in the caller's mailbox.


Put recovery rules outside the worker


OTP's gen_server behavior standardizes the request loop. An application supplies callbacks such as init/1, handle_call/3, and handle_cast/2. A counter callback can return {reply, Next, Next}: one value for the reply and another for the next state [4].


A supervisor starts and monitors child processes. Assuming permanent children, one_for_one restarts the failed child, one_for_all restarts the group, and rest_for_one restarts the failed child and those started after it. Restart intensity limits repeated restarts within a configured time window [5].


Our spawn call does not attach the counter to a supervisor. If a replacement counter starts at zero, it does not recover the previous total. Persistent state, retry handling, and overload behavior still need application rules. The Akka/Scala comparison includes a supervision walkthrough.


Separate concurrency from throughput


This counter handles one update at a time. More clients can increase its mailbox without increasing that process's update rate. Independent counters can be split across processes. Message data is generally copied, with exceptions for reference-counted binaries and literals on the same node [3].
